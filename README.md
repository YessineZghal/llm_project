# LLM / RAG / Agents Research Assistant

A grounded question-answering app over a curated set of ~400 arXiv papers on
retrieval-augmented generation, LLM agents, and related NLP/ML topics. Built as
a project for [DataTalksClub's LLM Zoomcamp](https://github.com/DataTalksClub/llm-zoomcamp).

Every layer (retrieval, reranking, prompt) was evaluated against alternatives
before being wired into the app — see [Evaluation](#evaluation) for the actual
numbers, not just the claim.

## Problem

Researchers and practitioners who want quick, sourced answers about RAG,
LLM agents, and evaluation techniques currently have to manually search arXiv
and read abstracts one by one. This app answers natural-language questions
("How is hybrid search combined with reranking?", "What metrics are used to
evaluate LLM agents?") with a grounded, cited answer drawn from a curated
paper set, and can fall back to a live arXiv search for anything outside it.

## How it works

```
arXiv API ──▶ dlt ──▶ duckdb ──▶ data/raw/papers.jsonl
                                        │
                    ┌───────────────────┼────────────────────┐
                    ▼                   ▼                    ▼
             minsearch (text,    Elasticsearch (BM25,   sentence-transformers
              vector, in-mem)     kNN, RRF hybrid)        embeddings + cache
                    │                   │
                    └─────────┬─────────┘
                               ▼
                  cross-encoder reranker (best-practices)
                               │
                 ┌─────────────┴─────────────┐
                 ▼                            ▼
         RAG pipeline                  Agent (tool-calling)
   rewrite → retrieve → prompt   search_knowledge_base / search_arxiv_live
                 │                            │
                 └─────────────┬──────────────┘
                                ▼
                          Streamlit chat UI
                                │
                                ▼
                  Postgres (conversations + feedback)
                                │
                                ▼
                     Streamlit monitoring dashboard
```

Orchestration: a [Kestra](https://kestra.io) flow (`flows/ingest_arxiv.yaml`)
re-runs the ingestion pipeline daily, using the same Docker image as the app
so dependencies never drift between the two.

## Dataset

Fetched live from the free, public [arXiv API](https://arxiv.org/help/api)
(no key required) — 8 topic queries (RAG, LLM agents, tool use, prompt
engineering, LLM evaluation, vector search, hybrid search/reranking,
in-context learning) restricted to `cs.CL`, `cs.AI`, `cs.IR`, `cs.LG`,
deduplicated by arXiv id. The resulting ~400 paper metadata records
(title, abstract, authors, categories, URLs) are committed at
`data/raw/papers.jsonl` so the app runs immediately without hitting the API;
rerun `llm_project.ingest.pipeline` any time to refresh it.

## Tech stack

| Concern | Choice |
|---|---|
| LLM | OpenAI (`gpt-4o-mini` for answers and as the LLM judge) |
| Knowledge base | minsearch (in-memory) + Elasticsearch (BM25 / kNN / hybrid) |
| Reranking | `cross-encoder/ms-marco-MiniLM-L-6-v2` |
| Embeddings | `sentence-transformers/all-MiniLM-L6-v2` |
| Agent tools | [toyaikit](https://github.com/alexeygrigorev/toyaikit) tool-calling loop |
| Ingestion | [dlt](https://dlthub.com) → duckdb, orchestrated by [Kestra](https://kestra.io) |
| Interface | Streamlit (chat + monitoring dashboard) |
| Monitoring | Postgres (conversations + feedback) → Streamlit dashboard |
| Containerization | Docker Compose (app, Elasticsearch, Postgres, Kestra) |

All dependency versions are pinned via `uv.lock`.

## Evaluation

### Retrieval: 6 methods compared on 160 LLM-generated questions (`data/eval/ground_truth.csv`)

Ground truth was generated by asking an LLM for questions each of 80 sampled
paper abstracts would answer (`llm_project.eval.generate_ground_truth`), then
every method in `retriever.METHODS` was scored on hit-rate@5 and MRR@5
(`llm_project.eval.evaluate_retrieval`):

| method | hit_rate@5 | MRR@5 |
|---|---|---|
| **es_hybrid_rerank** | **0.988** | **0.981** |
| es_hybrid | 0.975 | 0.928 |
| es_knn | 0.950 | 0.879 |
| minsearch_vector | 0.950 | 0.877 |
| minsearch_text | 0.925 | 0.865 |
| es_text | 0.919 | 0.841 |

`es_hybrid_rerank` (Elasticsearch BM25 + kNN fused via Reciprocal Rank Fusion,
then cross-encoder reranked) wins clearly and is the default retrieval method
in the app (`retriever.py`, `rag/pipeline.py`). Full results:
`data/eval/retrieval_eval_results.csv`.

### Answer generation: 2 prompt variants judged by an LLM

Both variants (`strict` — context-only, must cite every claim; `concise` —
short and direct) were run against the same 25 sampled questions and retrieved
context, then scored 1–5 on relevance/groundedness/clarity by an LLM judge
(`llm_project.eval.evaluate_rag`):

| variant | relevance | groundedness | clarity | overall |
|---|---|---|---|---|
| **strict** | **4.52** | **5.00** | **4.96** | **4.76** |
| concise | 4.36 | 5.00 | 4.92 | 4.68 |

`strict` wins and is the default prompt variant. Full results:
`data/eval/rag_eval_results.csv`.

Both evaluations are reproducible:

```bash
uv run python -m llm_project.eval.generate_ground_truth
uv run python -m llm_project.eval.evaluate_retrieval
uv run python -m llm_project.eval.evaluate_rag
```

## Monitoring

Every chat turn (RAG or Agent mode) is logged to Postgres — question, rewritten
search query, answer, retrieval method, prompt variant, response time, and
cited source doc ids — and every 👍/👎 vote is logged against it
(`src/llm_project/db/`). The **Monitoring** page in the Streamlit app
(`src/llm_project/app/pages/1_Monitoring.py`) reads that data and shows:

- KPI tiles: conversation count, feedback count, 👍 rate, average response time
- Conversations per day
- RAG vs Agent mode split
- Retrieval method usage
- Response time distribution
- Feedback breakdown (👍 vs 👎)
- Most-cited source papers

## Running it

### Docker Compose (everything)

```bash
cp .env.example .env   # fill in OPENAI_API_KEY at minimum
docker compose up --build -d app elasticsearch app_postgres
```

This starts Elasticsearch, the app's Postgres (for conversations/feedback),
and the Streamlit app (`http://localhost:8501`) with the dataset already
present in `data/raw/papers.jsonl`. The Elasticsearch index is empty until you
build it once:

```bash
docker compose exec app python -m llm_project.search.es_index
```

(`--recreate` rebuilds it from scratch, e.g. after re-running ingestion.)

Add `kestra kestra_postgres` to the `up` command (or run `docker compose up
--build -d` with no service list, to start everything) if you also want the
orchestration UI at `http://localhost:8080`, which runs the daily ingestion
flow in `flows/ingest_arxiv.yaml`. Note: refreshing the dataset via that flow
does not automatically rebuild the Elasticsearch index — rerun the command
above (with `--recreate`) afterward.

### Manual / dev setup

```bash
uv sync
cp .env.example .env   # fill in OPENAI_API_KEY

# Elasticsearch + app Postgres only, without the app container:
docker compose up -d elasticsearch app_postgres
uv run python -m llm_project.search.es_index

uv run streamlit run src/llm_project/app/streamlit_app.py
```

To refetch the dataset from arXiv instead of using the committed snapshot:

```bash
uv run python -m llm_project.ingest.pipeline
uv run python -m llm_project.search.es_index --recreate
```

minsearch-based retrieval methods (`minsearch_text`, `minsearch_vector`) work
without Elasticsearch or Postgres at all — only `OPENAI_API_KEY` and
`data/raw/papers.jsonl` are required.

## Project structure

```
src/llm_project/
  config.py           # env vars, paths, model/index names
  ingest/
    arxiv_source.py    # arXiv API client
    pipeline.py         # dlt -> duckdb -> data/raw/papers.jsonl
  search/
    minsearch_index.py  # in-memory text + vector search
    es_index.py          # Elasticsearch text/kNN/hybrid + index build CLI
    embeddings.py         # sentence-transformers, disk-cached
    rerank.py              # cross-encoder reranking
    retriever.py            # single dispatch point over all 6 methods
    load_docs.py             # loads data/raw/papers.jsonl
  rag/
    pipeline.py          # rewrite -> retrieve -> prompt -> generate
    agent.py               # tool-calling agent (knowledge base + live arXiv)
    query_rewrite.py         # conversational question -> search query
    prompts.py                # strict / concise answer prompt variants
  eval/
    generate_ground_truth.py  # LLM-generated (doc_id, question) pairs
    evaluate_retrieval.py      # hit-rate@k / MRR@k across all methods
    evaluate_rag.py              # LLM-judge comparison of prompt variants
  db/
    models.py             # SQLAlchemy models: Conversation, Feedback
    client.py               # log_conversation, log_feedback, dashboard queries
  app/
    streamlit_app.py       # chat UI (RAG + Agent modes, feedback buttons)
    pages/1_Monitoring.py    # monitoring dashboard
flows/ingest_arxiv.yaml    # Kestra flow: daily ingestion
docker-compose.yml          # app, elasticsearch, app_postgres, kestra
Dockerfile
```

## Example questions

- What is retrieval-augmented generation?
- How is hybrid search combined with reranking?
- What metrics are used to evaluate LLM agents?
- What are common approaches to prompt engineering?
- Find recent papers on tool-use benchmarks for LLM agents. (Agent mode —
  the curated set may not have the very latest papers; the agent falls back
  to a live arXiv search.)

## Limitations

- The knowledge base is a snapshot (~400 abstracts across 8 topics as of the
  last ingestion run), not the full arXiv corpus — the agent's
  `search_arxiv_live` tool covers gaps for recent or out-of-scope papers.
- Answers are grounded in paper *abstracts* only, not full text.
- Refreshing the dataset via the Kestra flow does not automatically rebuild
  the Elasticsearch index (see [Running it](#running-it)).
- Evaluation ground truth is LLM-generated, not human-labeled.
